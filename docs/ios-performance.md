# iOS 对话性能优化

日期：2026-09-29。范围：原生 iOS 对话、Runtime 历史分页和实时订阅。保留同一 Runtime 的持久历史和多端去重协议。

## 实现

- 草稿/待发送意图与历史缓存分开保存；旧格式自动读取迁移，未读取成功的数据不会静默覆盖
- 每个文件按提交顺序在后台编码和原子写入；快速切回同一实例会等前一次写入，避免旧草稿覆盖新内容
- 输入合并 300ms 后保存；发送意图立即持久化，写入成功后才网络提交；原音清理也等待队列更新保存成功
- 可重建的历史缓存最多约每两秒合并写入，完成回复立即提交；空事件和完全相同的消息不触发缓存保存
- 单条消息拥有稳定可观察对象，已有消息更新不重新排序；仅插入消息时排序，输入框、播放进度和消息正文分开观察
- 系统 `List` 按需复用消息行，运行时窗口最多 500 条，磁盘缓存最多 200 条；上翻时维持窗口，提供回到最新页入口
- 照片在后台直接缩图后上传/显示，解码图片缓存限制为 24MB；语音暂停和继续不重新下载原件
- Runtime 为 `version` 建立索引，空闲版本相等时跳过消息表查询；历史单页最多 100 条，增量补读每批最多 100 条
- 补读按修改版本排列，游标推进到本批已交付版本；期间旧消息再更新会进入后续批次
- 最新页和离线缓存无交集时重建最新窗口，避免分页游标跳过中间未加载的历史

原生列表保留现有气泡、语音条和 Selfcraft 语义颜色。长消息下的滚动定位需要单独验证，不能仅把 VStack 替换成 LazyVStack 就认为完成。滚动 API 行为参考 [Apple 滚动定位文档](https://developer.apple.com/documentation/swiftui/view/scrollposition(_:anchor:))。

## 测量

同一 Docker 环境，独立临时 SQLite 数据库，10,000 条各含 200 字符的合成消息。预热 20 次，再连续调用 1,000 次无新消息的订阅查询。

| 指标 | 优化前 | 优化后首次同条件复测 |
| --- | --- | --- |
| 1,000 次空闲查询总耗时 | 739.0ms | 6.9ms |
| 从版本 1 补读的第一批消息数 | 9,999 | 100 |
| 版本查询计划 | 全表扫描和临时排序 | `conversation_version` 索引 |

复现命令：`bun run bench:conversation`。后续一次复测为 4.7ms；耗时受机器负载和缓存影响，不作固定时延承诺。

iOS Debug 模拟器测试按 100 条一批合并 10,000 条合成消息，约 55ms，最终保留 500 条。此项只测状态合并，不包括 UI 绘制、网络和真机磁盘；不能将其解释为滚动帧率提升。尚未取得真机 Instruments 帧率、耗电和内存峰值的前后对照。

## 验证

- Runtime 类型检查、202 项测试、doctor、evolution/provider smoke 通过
- 显式测试环境变量的真实模型 smoke 通过
- iOS 10 项测试通过，覆盖稳定行身份、空/重复事件、万条数据窗口上限、历史浏览不被新消息挤走、旧缓存迁移、草稿与缓存隔离、并发保存顺序、重连历史缺口
- Debug、Release 模拟器构建通过
- 本地测试实例重启后，Web Cookie、原生 Bearer、CLI 实时订阅及重复提交去重通过
- 模拟器上翻后，从其他入口发消息，原可见内容保持不变；出现回到最新消息入口，点击能读取新回复
- 通过真实长消息历史检查首次定位，原件仍可手动播放
- 在模拟器输入测试草稿，停止并重新启动 App 后恢复同一草稿和最新消息；验收后清除测试草稿

优化不删除 Runtime 原始历史，也不改变任务执行和原始音频保留规则。真机长时间使用与极端媒体内容的帧率/内存仍需后续测量。
