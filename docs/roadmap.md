# 路线规划

本文按 [产品目标](product-goal.md) 规划实现顺序，并遵守 [ADR 0001：助理定位](adr/0001-assistant-positioning.md) 的原则。产品目标是越用越懂、越用越帮；两条承诺是产品追求：同样的话，不用说第二遍；同样的错，不犯第二次。

- 更新日期：2026-10-03

## 推进原则

- **先解决真实问题**：从用户确实反复遇到的问题出发，让用户在下一次相似交互中感受到“这次它记住了，也用对了”
- **先人工诊断，再自动化**：检查步骤反复被证明有用后才自动化，不预先建设检测与归因系统
- **逐阶段验证**：每个阶段通过验证后才进入下一阶段；验证不通过就停在当前阶段调整
- **复用优先**：优先使用已有的事件、记忆、事项、Job、Reflection 与通知机制，不预先建立实体
- **不为显得鲜活新增活动或模型调用**：涉及模型调用的后台活动受预算约束
- **真实使用决定方向**：自动化测试只证明机制正确，是否越用越懂需要在真实使用中检查

## 阶段总览

| 阶段 | 目标 | 核心内容 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 零 | 语义与约定 | 系统提示词、Reflection 提示词；可与阶段一并行 | 检查全部通过 |
| 一 | 解决真实的重复问题 | 少量真实案例的诊断、修复与验证，可针对多个问题重复 | 用户在相似交互中感受到“这次它记住了，也用对了” |
| 二 | 检查自动化与防止退化（按需） | 把反复有用的检查步骤自动化；回放回归 | 人工诊断已证明有用；模型或 Runtime 变更时能发现退化 |
| 三 | 可见的复利 | 变化讲述、“记在心上的事”验证、空间 | 按优先级安排，另行设计与验证 |
| 四 | 能力成长衔接 | 重复失败作为成长候选的证据 | 另行设计与验证 |

改动小，不改变数据结构，可与阶段一并行，不阻塞。状态：已完成（2026-10-03）。

| 身份归属 | `src/memory/reflection-worker.ts`、`src/tools/memory-tools.ts` | 说明助理自身的身份描述写入 `IDENTITY.md`，不写成 `identity` 记忆 | 已完成 |
| 立场规则 | `src/agent/agent-runtime.ts` 的 `buildInstructions` | 行为上让步，认识上按证据更新；与用户意见一致本身不是问题；不以迎合换取更少的纠正 | 已完成 |
| 内核约定 | 同上 | 不修改 `HANDBOOK.md` | 已完成，仅为指令约定，未加技术保护 |
| 依据与确认 | 同上 | 依据推测而非用户明确表达的理解作决定时，简短说明依据；理解只是推测或可能过时，且与当前事情相关时，先确认再使用 | 已完成；推测的确认在此前已通过 `pending-understanding` 实现 |
| 系统事实 | 同上的 `<runtime-context>` | 目前提供时间、时区、入口与是否可联网。逐项评估视觉能力、后台预算上限、自我演化是否可用等，只补充会影响助理判断的信息 | 已评估，暂不新增，见下 |

系统事实的评估结论：

- **联网**：已按是否配置网络访问切换指令与工具，无需重复
- **视觉能力**：当前模型不读图时，历史图片会替换为提示改用 `image_analyze` 的占位文字；没有视觉模型时 `image_analyze` 返回明确错误。唯一的缺口是用户发图之前就问“能不能看图”，影响小，暂不补充
- **后台预算**：由 Runtime 确定性执行，达到上限时事项被标为阻塞并写明原因，助理不需要预先知道上限来做判断
- **自我演化**：工具始终暴露，不可用时返回明确原因
- 真实使用中出现因缺少系统事实而判断失误的案例时，再按案例补充

## 阶段一：解决真实的重复问题

目标：选出用户确实反复遇到的问题，找到学习在哪一环断了，修复最常见的一处，并在相似交互中验证。可以针对多个问题重复这个过程。

### 1a. 选择案例

- 用户直接指出自己反复遇到的问题
- 在对话历史中检索表示重复的说法，例如“我说过”“又”“不是说了”
- 只选少量、用户明确指出过的重复问题
- 读取本地实例数据需要用户授权，只读进行

### 1b. 逐个诊断

先排除不算重复的情况：用户改变了主意、网络故障等不可控的失败、上一次纠正的适用条件不覆盖新的情境。

其余案例按下面的清单核对断点。这是诊断清单，不是需要预先开发的系统：

| 断点 | 判断依据 |
| --- | --- |
| 没保存 | 没有对应的记忆 |
| 没生效 | 对应的记忆仍是候选 |
| 没召回 | 对应的记忆有效，但没有进入当次上下文 |
| 没用对 | 对应的记忆进入了上下文，助理仍然没有正确使用 |

- 记忆的 `knownFrom` 与 `knownTo` 可用于判断当时某条认识是否已经生效
- 如果现有数据无法区分“没召回”与“没用对”，且案例确实需要区分，再补充最小的记录：每次运行实际注入了哪些记忆。目前 `executions` 只保存输入与消息，不保存当次指令，无法事后得知注入了哪些记忆
- 注意反应与做法的关联：用户对某个做法的反应，通常出现在下一次运行中。诊断时要确认反应针对的是哪一个做法

### 1c. 修复最常见的断点

从下面的候选修复中，选择与诊断结果对应的一项，不要求全部做。

**没保存：让 Reflection 看见做法与反应**

现状：

- Reflection 读取整次运行的事件，包括用户输入、助理回复、工具调用与结果、运行失败
- 检索已有记忆时同时使用运行内事件、用户反馈前最近的一条前台回复与相关话题（`reflection-worker.ts` 中的 `existing`）
- 最近的前台回复作为 `preceding-replies` 提供，只用于理解用户反馈，不能作为学习证据引用
- 有具体行为依据的用户推测可以保存为 `inferred` 候选；已有成长候选按 `targetId` 增强，不按标题重复新建
- Runtime 因预算或异常把事项标为阻塞时不产生事件，尚未进入 Reflection

仍可改进：

- 事项阻塞作为失败事件进入 Reflection
- 提炼对用户的理解与做法上的教训；已由 `preference` 覆盖的内容不重复写成 `lesson`；关于用户的推测保持候选
- 难点：Reflection 按运行处理事件，空闲时会合并连续运行一起回看，这能覆盖一部分跨运行的反应，但需要确认关联是否可靠。关联错误会学到错误的认识

**没生效：补充生效路径**

现状：

- 用户明确表达、来源全部为用户事件的认识自动生效（`memory-store.ts` 中的 `canActivate`）
- 已验证的具体错误已实现执行纠错部分：同一次运行中失败、改正后的工具调用与对应结果可核对，且不涉及对用户的推断时，`lesson` 自动生效并保留 `observed` 依据，正文必须包含适用条件（`isVerifiedCorrection`、`activateObservedMemory`）。“用户确认了改法”走 `memory_confirm`，依据变为 `stated`
- `reinforce` 补完来源后，只有本次证据满足上述两种条件、且正文与类型不变时才激活候选；从多段经历概括的规律仍没有生效路径
- 候选可以被 `MemoryStore.search` 检索，供 Reflection 与 `memory_search` 继续核验，但常规上下文的召回路径会排除候选。前台只会把少量相关的 `inferred` 候选作为 `pending-understanding` 提供，供助理在相关时确认
- `confirmMemory` 激活时会把依据改为 `stated`

改为：

- **用户明确的纠正**：沿用现有规则，立即生效
- **已验证的具体错误**：同一段经历中改正后的做法确实成功，或用户确认了改法，立即生效；保留 `observed` 依据，并写明适用条件（执行纠错部分已实现）
- **从少量经历概括出的规律**：至少两个独立的“做法—结果”实例支持同一认识，且没有尚未解决的反证或归因歧义，才自动生效
    - 确定性下限：每个实例必须包含一个结果事件，即用户的反应或系统记录的失败，助理自己的发言不算；同一事项的重试与接续、同一段连续运行中的选择与纠正，只算一个实例
    - 内容判断：Reflection 需要说明支撑实例为何彼此独立，以及是否存在反证或归因歧义
- **补证据后重新判断**：`reinforce` 补完来源后重新评估生效条件，第二次印证的正常路径才能激活候选（目前只对明确陈述与执行纠错重新判断）
- **保留依据性质**：经历学习的自动生效不复用 `confirmMemory`，生效后保留 `observed` 或 `inferred`
- **关于用户的推测**：包括被表述为协作经验的推测，仍需用户确认。助理在推测与当前事情相关时自然地确认，用户同意后通过 `memory_confirm` 激活，这时依据是用户的明确表达
- 用户仍可通过记忆页查看、纠正、忘记

**没召回：改进检索或上下文组装**

具体做法按诊断案例决定。

**没用对：调整指令或提示方式**

具体做法按诊断案例决定。

**隐式信号不足：补充显式预期记录（按需）**

例如对耗时与风险的预估。范围与形式届时再定。

### 1d. 验证

- **同一批案例**：修复后在相似情境中重新检查，不执行有副作用的工具
- **后续真实使用**：在相似交互中，用户感受到“这次它记住了，也用对了”
- **没有迎合迹象**：有理由的异议仍然存在，纠正减少不是因为助理回避判断

按修复内容执行对应的自动化检查：

- 阶段零的全部检查，以及使用显式环境变量执行真实模型验收 `bun run smoke`。它使用替代的 Reflection，不能证明学习成立
- 修改 Reflection 或生效规则时，补充单元测试：
    - 用户明确的纠正立即生效
    - 已验证的具体错误立即生效，依据为 `observed`，并带有适用条件
    - 概括的规律只有一个独立实例时保持候选，两个独立实例经 `reinforce` 补证据后生效
    - 同一事项的多次运行、选择与随后的纠正、助理的复述，不会凑够门槛
    - 关于用户的推测，包括被表述为协作经验的推测，不会自动生效
- 修改 Reflection 或生效规则时，扩展并执行 `bun run smoke:memory`，它运行真实 Reflection，需要覆盖：
    - 做法与后续反馈能够正确关联
    - 已验证的具体错误能立即影响下一次行为
    - 重复转述、同一失败的多次运行不会凑够概括规律的门槛
    - 关于用户的推测被包装成 `lesson` 时不会自动生效
    - 生效认识能够进入后续上下文，并影响相关行为

## 阶段二：检查自动化与防止退化（按需）

### 2a. 检查自动化

只在人工诊断反复被证明有用之后进行，只自动化被证明有用的步骤：

- 纠正与失败记录：情境、助理的做法、用户的期望或失败原因、类别与来源事件；存储优先复用现有结构
- 重复线索：同类问题在新情境中再次出现时标记为线索，不直接判定没有学会
- 注入记录：如果阶段一尚未补充
- 只读报告：被标记的案例供用户定期确认
- 可以对已有历史回溯标记；回溯会消耗模型调用，范围由用户决定

### 2b. 回放回归

- 把被纠正过的情境保存为回放案例
- 模型或 Runtime 变更时重跑，不执行有副作用的工具
- 回放只能证明没有遗忘，不能证明懂
- 之后可以评估把回放纳入 `EvolutionService` 的候选验收

验证：自动标记与人工判断基本一致；回放结果稳定，变更后能够发现退化。

## 阶段三：可见的复利

按优先级排在学习改进之后，但不以完整的学习体系为前提。届时单独编写设计文档。

### 3a. 两次见面之间的变化讲述

- 由确定性逻辑汇总用户上次离开后的事项状态变化、Job 完成、新生效的认识与收件箱通知，在下一次前台对话时作为数据注入上下文，由助理判断是否值得提及。不新增模型调用
- 按事项推进、Agent Job 与 Reflection 分类统计后台模型用量，观察一段时间后再决定预算上限
- 沿用 `WorkRunner` 在已有授权内推进事项，不扩大授权范围

### 3b. 验证节点：它记在心上的事

空间要表达“它记在心上的用户的事”，例如用户正在推进的目标、用户提过的重要日子。表达这一类内容之前，先验证这种状态是否真实成立，避免空间被实现成固定的任务状态映射：

- **来源**：由什么真实经历产生
- **保留**：存放在哪里，优先复用现有的 Topic、Work 或记忆，不预设新增实体
- **更新**：在什么条件下延续、改变或放下
- **影响**：如何同时影响行动（例如适时跟进）与表达
- **出口**：如果它既不影响行动，也说不出真实来源，就记录为不成立，空间不表达这一类内容

### 3c. 空间

1. `AssistantMurmur` 改为来自真实状态，例如变化讲述、进行中的事项，以及验证成立的“记在心上的事”
2. Web 端空间的 MVP：按产品目标表达一起完成的事、为用户长出的能力与此刻的状态，这些可以直接使用已有材料；“记在心上的事”等待 3b 的结论。场景数据与 2D 渲染，每件都可以点开查看依据，并接受用户的反馈
3. 验证手感后再评估 three.js 等更重的渲染方案，同时验证性能、浅色与深色主题、减少动效与移动端布局

## 阶段四：能力成长衔接

- 反复发生的同类失败作为成长候选的证据，接入现有的 `GrowthProposal` 与 `EvolutionService`
- 阶段二的回放案例可以作为演化候选的回归标准
- 届时单独设计
