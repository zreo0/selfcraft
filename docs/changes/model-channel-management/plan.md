# Web 模型渠道与模型管理交互优化：方案

## 方案

采用“渠道列表内管理模型、独立表单提交、服务端按操作限制写入范围”。沿用现有配置结构与组件库，不增加数据库、配置版本、中心注册表或状态框架。

### 页面与操作

设置页保留两个分区：

1. **模型用途**：默认模型选择器，以及现有反思、上下文整理和推理强度设置；选项显示 `渠道 / 模型`，反思与整理支持“跟随默认”
2. **渠道与模型**：顶部“新增渠道”，每个渠道展示标识、协议、地址、凭证状态，提供“编辑渠道”和“添加模型”；下方模型行展示能力、用途标签及测试、编辑、删除入口

不再保留“添加或更新渠道”长表单，也不通过填写已有标识推断编辑意图。

| 入口 | 字段与行为 | 成功后的反馈 |
| --- | --- | --- |
| 新增渠道 | 独立 Dialog，填写渠道标识、协议、地址与 Key；标识不预填 `default`，避免诱导重复使用；重名时就地报错 | 更新渠道列表，并打开该渠道的“添加模型”；取消添加模型时保留空渠道 |
| 编辑渠道 | 固定渠道标识，只编辑协议、地址和 Key；表单内持续显示“影响该渠道下的 N 个模型”；Key 留空保留，不回显 | 只更新连接信息，保留模型、用途和推理设置；明确显示已保存 |
| 添加模型 | 固定所属渠道，只填写模型 ID、视觉能力、上下文窗口和最大输出 Token；使用现有能力默认值 | 添加到渠道下；已有默认模型不变；同渠道重名时报错并提供编辑入口 |
| 编辑模型 | 固定渠道与模型 ID，只修改模型能力参数 | 只更新目标模型，保留渠道与用途配置 |
| 删除模型 | 打开确认 Dialog，展示完整渠道与模型标识、当前引用用途及删除影响 | 无引用时确认删除并更新列表；有引用时不提供可执行的确认删除按钮，提供“前往模型用途”入口 |

引用保护以默认模型及显式的反思、上下文整理配置为准。默认模型同时被其他用途继承时，提示其继承用途，但不制造额外配置；用户切换默认后，继承用途自然跟随。独立用途须切换到其他模型或恢复“跟随默认”。唯一默认模型显示“先添加替代模型并切换默认”。

删除渠道最后一个未被引用的模型后，保留渠道及凭证，展示“暂无模型”和添加入口。模型支持图片时，在删除确认中提示它也可能用于图片分析；不额外禁止删除，不新增“视觉默认模型”配置。

对话框每次按目标初始化草稿，成功或关闭后清空 Key；请求失败保留必要输入并显示错误。一次页面操作期间禁止重复提交和冲突操作；成功后使用接口返回的完整脱敏配置更新页面。失败或响应丢失时不宣称成功，可重新读取 Runtime 状态核对，不自动重试变更请求。

复用现有 Dialog、Button、Input、Combobox、Select、Switch 与语义色。保存、删除错误使用可访问提示，关闭 Dialog 后恢复焦点；键盘可以完成操作。窄屏使用上下排列的渠道头和按钮，不依赖悬浮显示操作。

### 首次配置与空渠道恢复

Web 首次配置仍允许一次提交“新渠道 + 首个模型”，按两个明确分组展示字段，共用渠道字段及模型能力字段，不再共用原先兼具新增和编辑行为的提交逻辑。服务端校验完整请求后保存，不拆成两次 HTTP 请求。

尚无可用默认模型时，新增空渠道后 `configured` 仍为 false；不能仅因渠道保存成功就进入时区步骤。已有可用默认模型时，新增空渠道不改变配置可用状态。刷新页面再次进入 onboarding 时，读取已有渠道，提供“使用已有渠道添加模型”与“新增渠道”；已有渠道选中后只显示连接摘要和模型字段，不重新要求填写地址、Key。已有模型但尚未有有效默认选择时，引导去完整设置选择模型或修复连接，避免用同名创建覆盖修复。

只有默认选择为空时，首次创建的模型自动成为默认；已有默认选择时，新增渠道或模型均不切换用途。配置中遗留的无效默认引用不借新增操作静默替换，用户从用途选择显式修复。

### Runtime 接口与持久化

复用现有固定路径和 JSON 请求体风格，模型 ID 留在请求体中，避免模型 ID 含 `/` 时的路径解析歧义。所有变更继续使用现有鉴权、同源检查和 `application/json` 要求。

| 请求 | 允许输入 | 语义 |
| --- | --- | --- |
| `POST /api/config/providers` | 渠道字段，可带首个模型字段或 `models` | 仅创建新渠道；兼容旧客户端两种模型输入形状，但不兼容重名覆盖；省略模型时创建空渠道，两种模型形状同时出现时拒绝 |
| `PUT /api/config/providers` | `providerId`、协议、地址、Key | 仅更新已存在渠道的连接信息；禁止模型字段；省略或清空可选地址表示恢复官方默认地址，兼容协议仍要求地址 |
| `POST /api/config/models` | `providerId`、`modelId`、能力参数 | 仅给已存在渠道新增模型；目标模型重名时报错 |
| `PUT /api/config/models` | `providerId`、`modelId`、能力参数 | 仅更新已存在模型；标识只用于定位，不支持改名或搬迁 |
| `DELETE /api/config/models` | `providerId`、`modelId` | 检查最新用途引用后删除；不清理渠道、凭证或用途引用 |
| `PUT /api/config/model` | 现有用途选择输入 | 保持原有用途切换语义，与模型增删改接口区分 |
| `POST /api/config/model/test` | 现有测试输入 | 保持流式连接测试，不产生会话，不隐式保存草稿 |

渠道与模型变更请求采用严格字段白名单，越界字段直接拒绝；尤其不能把模型请求中的地址或 Key 静默当成渠道更新。输入错误、目标不存在、重复创建及被引用等业务失败沿用现有 `400 + { error }` 风格，并返回可读错误；不为本次变更引入通用错误框架。删除被引用时，错误列出具体用途。成功响应仍为现有 `ConfigView`，不新增凭证字段。

在 `ConfigStore` 内将现有 `addProvider` 收紧为仅创建，新增明确的 `updateProvider`、`addModel`、`updateModel`、`deleteModel` 方法。复用必要的标识、连接和能力校验，不保留可被 HTTP 调用的隐式合并覆盖入口；测试中原本用 `addProvider` 更新的场景改为显式操作。创建渠道允许空 `models`，保持 `version: 1`、`credentialRef` 和 `modelOverrides` 数据结构。

所有业务校验应在写文件前完成；重复渠道、重复模型、引用阻止及越界请求不得改动配置或凭证。模型操作只写 `config.json`，绝不写 `secrets.json`；渠道创建和更新沿用已有密钥校验、空 Key 保留及无 Key 兼容接口规则。

删除在单次同步方法中读取最新配置、检查默认与独立用途引用、删除并保存，中间不插入 `await`。这适用于项目的唯一 Runtime 写入边界，避免另一客户端在页面打开后切换用途导致误删。继续复用单文件原子替换，不增加锁或事务层。渠道配置和凭证的两文件写入仍非跨文件事务，不宣称具备断电级整体回滚；本次不扩展为持久化架构重写。

### 客户端兼容取舍

已比较以下两种方案：

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 新增 Web 专用严格接口，旧接口保留覆盖 | CLI、iOS 不必适配 | 误覆盖入口继续存在，后端新增语义不一致；不采用 |
| 收紧共享创建接口，CLI、iOS 做必要提示适配 | 所有入口重名新增均不能覆盖，规则统一 | CLI、iOS 不再通过旧表单更新已有渠道；用户已确认采用 |

CLI `/model add` 和 iOS 原设置表单保留创建新渠道及初始模型；取消“已有渠道留空保留”和“添加或更新”这类暗示可编辑的提示，说明已有渠道请通过 Web 管理。保留各自现有模型选择、连接测试能力，不为 CLI 新增测试命令，不为 iOS 复制本次 Web 管理界面。重名错误由服务端兜底，即使旧客户端未升级也只能得到错误，不能覆盖配置。

保留旧客户端单模型输入、CLI 多模型输入和脱敏响应形状。因此旧客户端创建新渠道仍可用；重名更新被拒绝属于此次明确批准的行为变化，需要在 README 或相应入口说明中记录。

### 代码组织

- `src/config/types.ts`、`src/config/config-store.ts`：定义实际使用的操作输入和写入规则，保留既有配置结构
- `src/web/web-server.ts`：拆分严格请求校验、路由与存储调用；不顺手拆分整个服务文件
- `web/src/types/api.types.ts`、`web/src/services/runtime.ts`：拆分渠道和模型输入及请求函数，删除因本次替换失去调用方的混合接口封装
- `SettingsView/index.tsx`：编排用途区、渠道列表与操作状态；`ModelList.tsx` 调整为渠道内模型列表，沿用测试逻辑；`ProviderForm.tsx` 限定为渠道表单
- 按真实复用需要提取同目录的模型表单、用途设置与字段组件，供设置页和首次配置组合；不建立通用表单框架或集中状态管理
- `OnboardingView/index.tsx`：接入明确的创建流程及已有空渠道恢复路径
- `src/onboarding/onboarding.ts`、`ios/Selfcraft/Features/SettingsView.swift` 及对应文档：只做创建语义相关的提示适配；客户端请求类型随实际需要收紧
- `web/src/styles/globals.css`：只调整本次渠道层级、模型行和表单布局需要的样式

## 影响

| 可能影响 | 依据 | 如何确认 |
| --- | --- | --- |
| 原有数据和空渠道 | `config-store.ts` 的 schema 已允许空模型映射；`buildConfigView` 按渠道和模型分别遍历 | 旧配置读取测试、空渠道往返持久化与刷新验证；不进行迁移 |
| CLI、iOS 及旧浏览器页面 | `runtime-client.ts`、`ModelSettings.save`、原 `ProviderForm` 均调用同一 POST 接口 | 覆盖旧输入形状创建成功、重名请求失败且无写入；更新提示并说明需刷新 Web |
| Web 首次配置 | `OnboardingView` 复用旧表单，`App.load` 根据 `configured` 打开 onboarding | 空实例、新渠道带首模型、空渠道刷新继续配置均实测；仅有效模型配置后推进步骤 |
| 默认与后台用途 | `ConfigStore.getModel` 根据独立用途或默认选择解析模型，`read` 会容错清理旧失效覆盖 | 删除前主动拒绝引用，测试不能依赖读取时的容错来完成删除；保留推理强度 |
| 隐式视觉模型 | `ModelFactory.createVision` 会扫描全部模型，选择可用视觉能力 | 验证删除未引用视觉模型后重新选择剩余模型或返回无可用模型；删除提示说明影响 |
| 正在运行的任务和上下文整理 | `ModelFactory.create` 生成模型快照；`AgentRuntime.assertContextConfig` 会因配置变化放弃旧条件下的整理 | 不修改 Agent Loop；保留既有快照及整理回归测试，不承诺所有进行中的工作完全不受配置变化影响 |
| 凭证与其他设置 | 配置、凭证分别落盘，同一个凭证文件还保存其他服务凭证 | 模型操作不改变凭证文件内容；渠道更新保留其他凭证；响应和错误不含 Key |
| 多客户端陈旧页面 | 页面配置不会因所有其他入口的变更自动同步 | 用接口测试模拟先切换引用再删除，删除必须基于服务端最新状态被拒绝；失败后允许刷新核对 |
| 原有脚本和单元测试 | 脚本使用 `addProvider` 初始化；部分测试用它更新同名渠道 | 检索并区分创建与更新调用，更新语义测试迁移到显式方法，不批量重写无关测试 |

## 发布和回滚

不迁移配置版本。Runtime 与 Web 构建产物配套更新，记录 POST 接口不再支持同名覆盖；旧 CLI、iOS 创建新渠道仍可用，更新客户端主要用于明确提示。已打开的旧 Web 页面应刷新，否则重名提交会得到拒绝。

回滚恢复配套代码和 Web 产物，无需反向数据迁移；空渠道属于旧 schema 已支持的数据。回滚代码不会恢复用户主动删除的模型或先前修改的凭证，不能把代码回滚描述为数据撤销。验证中只使用隔离数据，不通过备份、重置或覆盖用户现有凭证来验收。

### 实际交互验收

浏览器连接实际 WebServer / ConfigStore 和构建产物，数据保存在临时目录；Agent 使用测试替身，模型连接测试使用本地 SSE 兼容服务。没有修改用户实际渠道、凭证或历史。

- **渠道和模型隔离**：已复现 `dev` 重名创建被拒绝且连接不变；新增模型不出现地址或 Key 字段；重复模型引导编辑；编辑模型仅改变能力；显式编辑渠道时空 Key 保留凭证
- **删除和用途**：默认及独立反思用途阻止删除；反思可恢复跟随默认；未引用模型可删除，刷新后仍缺失；删除渠道最后一个模型后保留渠道与凭证；唯一默认模型提示先添加替代模型
- **并发与失败**：双击创建仅发出一次变更；实际保存后模拟回执丢失，页面显示错误且可读取最新配置恢复；删除确认打开后另一客户端新增用途引用，服务端拒绝删除
- **首次配置**：空实例创建渠道及首模型后进入时区步骤；已有空渠道只填写模型即可继续，连接字段不重复填写；配置未完成时不会提前推进
- **视觉与键盘**：桌面 1280 × 900、移动端 390 × 844 无横向溢出；澄蓝、墨白的浅深色及减少动效偏好已检查；Dialog 键盘焦点受控，“前往模型用途”落到默认模型选择器；最终协议按钮名称为“协议 OpenAI Compatible”
- **无障碍检查**：WCAG 2 A / AA 自动检查未报告违规；Radix 焦点哨兵有一项需要人工判断的结果，已实际验证 Tab 焦点保持在 Dialog 内；自动检查不等同于完整无障碍认证
